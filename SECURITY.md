# Security boundaries

This is a public education/community application, not a repository for Microsoft-confidential material, customer evidence, live tokens, or tenant credentials.

## Implemented controls

| Boundary | Implementation |
| --- | --- |
| Account authentication | Microsoft/GitHub authorization-code sign-in with server-side exchanges, S256 PKCE, one-use provider/browser-bound state; optional discoverable WebAuthn passkeys with required presence/verification, exact origin/RP ID, and ES256/RS256 verification |
| Provider identity | Microsoft RS256 verification through pinned jose, exact audience and tenant/issuer, issuer-scoped signing keys, expiry/issued time/nonce; GitHub authenticated immutable user ID through a fixed HTTPS API; no identity matching by email or display name |
| Replay and enrollment | Single-use, expiring challenges consumed atomically; flow identifiers stored as hashes; additional keys bound to the current fresh session; credential counters updated optimistically |
| Session exposure | 256-bit opaque identifiers; only SHA-256 hashes in D1; production `__Host-` session/passkey cookies with Secure, HttpOnly, Path=/, SameSite=Strict; separate ten-minute SameSite=Lax OAuth browser-binding cookie; fixed eight-hour session expiry and five-session cap |
| Cross-site mutations | Exact request URL/Origin checks, Fetch Metadata checks, required custom JSON request header, and session-bound CSRF tokens; no CORS access granted |
| Authorization | User and role resolved from D1 on each request; roles never trusted from the browser; explicit owner predicates; moderator role granted only through authenticated operator tooling |
| Site management | Exact immutable personal GitHub identity `8750972` (`oguzhanf`), rechecked through the live linked identity on every protected HTML/API request; not a handle, email, Microsoft-managed account, generic moderator role, or first-user grant |
| Member content | Server-only curriculum delivered by authenticated `/api/catalog`; default-deny API allowlist; protected HTML paths checked before assets are served; references/discussion reads require sign-in; no full course data in public JavaScript |
| Sensitive account/moderation actions | Site authentication within five minutes; provider reauthentication must resolve to the original session owner; linking requires a live, recent, consent-current owner session; deletion cascades active records; removing a method revokes other sessions and cannot remove the last available method |
| Abuse | Mandatory production Turnstile for registration and private-contact submission, including signed-in contact; no robot challenge for authenticated comments/questions/replies; server-side action/hostname checks where required; shared atomic salted-IP/account posting buckets; bounded inputs and 32 KiB request bodies |
| Public content | Plain-text React rendering, no user HTML/Markdown execution, strict CSP without unsafe-inline/eval, no framing, no referrer disclosure, nosniff and HTTPS headers |
| Discussions | Catalog-derived course forums, Site discussions, owner-only Announcements; one conversation per attached page; pending-by-default questions/replies; immutable parent relationships, depth-16 limit, 30-item sibling pagination, complete ancestor visibility checks, private moderation/reporting and audit context |
| Private contact | Public submission protected by same-origin JSON checks, managed Turnstile action/hostname validation, rate limits, secret/control-character rejection, and bounded messages; signed-in submissions require CSRF; request reads/resolution require a fresh moderator session |
| Source ingestion | Fixed public Microsoft HTTPS allowlist, no credentials/alternate ports, manual redirect rejection, bounded response bytes, hashing only; upstream text is not executed or auto-published |
| Launch | Public participation remains closed until the responsible operator approves policies and configures origin/RP ID, private contact, production bot controls, and private rate-limit salt |

The `local` exception is recognized only with the exact `http://localhost:8787` origin and `localhost` RP ID, for automated tests/development. Changing an environment-name string alone cannot turn off production protections. Never deploy the local environment as the site's host.

Public configuration exposes registration availability and the public widget/policy fields, not launch diagnostics. Missing operator details, approval, or secrets remain fail-closed conditions; only operator tooling reports their configuration requirements.

The shared source allowlist covers only the reviewed official Entra repository and Microsoft Learn Defender XDR, Graph API, Sentinel, and Partner Center announcement paths. Learn checks request Markdown and Graph checks pin the API version. The monitor only hashes fetched text; it never renders it as HTML or changes approved lesson content. HTTP/KQL lesson examples are escaped plain text and do not execute requests, run tenant queries, or acquire customer credentials.

Social authentication uses separate fixed Microsoft/GitHub HTTPS endpoints, bounded JSON/JWKS responses, and manual redirect rejection. Client secrets stay in Worker secrets; provider access/refresh tokens are transient and never enter D1, browser storage, or logs. Identity hashes include provider, issuer, and immutable subject. A new provider identity always starts as a learner; provider groups, roles, employer domains, emails, and display names grant no site role.

The **Site management** top-bar link is generated in the authenticated session response only for the pinned personal GitHub identity with current policy consent. The client never decides ownership from a user name. The URL is intentionally not a secret or bearer credential: `/management` and `/management/*` run Worker-first, and all `/api/management/*` routes enforce the owner check independently. Private management data/actions require a sign-in within five minutes, use no-store responses, and retain the normal CSRF/origin boundary on mutations. The same verified owner account may sign in with an optional linked passkey. Unlinking/replacing its GitHub identity removes management access immediately.

Existing explicitly granted moderators retain their limited discussion/contact review functions, but they do not receive the management link, account lists, overview, or management API access. The pinned owner can review through the management area without a generic moderator-role promotion. Account lists omit secrets, credential material, provider tokens/subjects, and other learners' quiz answers.

Announcements use `requireSiteManagement`, not a public handle or moderator role. Their initial post alone can publish immediately, with a review audit record. Creation requires current consent, CSRF, and authentication within five minutes; normal announcement replies remain pending. Transactional inserts repeat the live session, consent, and applicable immutable-owner predicate, so revocation between a preliminary check and the write cannot create a thread or orphan post.

Member HTML routes `/discussions` and `/discussions/*` run Worker-first, just like topics. Forums derive only from published catalog tracks; publishing an additional course needs no duplicated forum definition. Main pages map to Site discussions. Page/forum views address the same thread/node/comment identities. User titles, posts, replies, and moderation context are escaped plain text, never HTML or executable Markdown. Signed-in posting removes only the robot challenge, not origin/JSON/custom-header checks, CSRF, consent, moderation, or rate limits. Registration and public or signed-in private-contact submission still require real production Turnstile.

Roots are depth 0 and replies cannot exceed depth 16. Roots/independent threads use 30-item newest-first cursors; direct replies use 30-item oldest-first cursors. Replies are fetched per parent with bounded upward ancestry checks. A published descendant cannot reveal a different member's pending or hidden ancestor, its title, or its subtree. Reporting and posting repeat this boundary in the write itself. Moderation can review private ancestor context through its separate fresh-authorized queue; this does not broaden normal forum reads.

Migration 0004 adds immutable anonymous discussion nodes without rebuilding existing comments or report FKs. Account exports include post UUIDs, thread/category/parent identities, depth, and the member's initial-post titles, without other members' bodies. Removing a post erases body/title and clears reports atomically. Deleting an account cascades its original personal records, while deletion triggers retain anonymous structural context for other members' replies. Only an ancestor published **at removal** can leave a visible placeholder, and removed leaves are omitted. Empty removed branches in affected conversations are pruned in the same transaction, retaining every ancestor of every remaining live post, including private posts; no remaining post is truncated or reparented. A pending/hidden ancestor remains an inaccessible barrier after deletion; prior publication followed by hiding does not authorize a placeholder. No deleted user's handle, body, or question/announcement title is retained in the surviving topology. Account deletion and moderation use transactional identity-returning writes, not FK-inflated change counts.

Only the four explicitly allowlisted provider start/callback routes are public. Starts retain same-origin JSON/header checks; callbacks are the narrowly scoped GET exception because they return from an external provider. The callback instead requires the unexpired one-use state, correct provider, independent HttpOnly browser binding, PKCE, and verified identity. The Lax cookie is not a session and cannot read any member endpoint. Microsoft recent reauthentication requests `prompt=login`; GitHub requests account selection and a fresh code exchange, not an independent guarantee of a newly entered password or MFA.

## What the records mean

Reviewed lesson edits require the pinned personal owner, fresh site authentication, current consent, CSRF, the normal origin/JSON boundary, a reason, and explicit technical/privacy review confirmation. The same strict content schema validates catalog responses and edits, including the 100-word ceiling, reference membership, inert code, and bounded diagram nodes. Stable lesson/track/prerequisite identities cannot be changed through the editor. The D1 transaction repeats live session/CSRF, consent, freshness, immutable-owner, and expected-revision predicates before creating a history snapshot and publishing the override. Catalog reads and server grading resolve the same effective revision; stale learning submissions fail explicitly.

Screenshot edits accept only the privacy-reviewed local media registry, not arbitrary URLs, uploads, or unreviewed tenant captures. Preparation pins public Microsoft source bytes, crops/masks decoded pixels irreversibly, re-encodes without original metadata, and validates output fingerprints. A changed upstream image requires a new visual privacy review rather than automatic approval. The included screenshots come from Microsoft documentation, not an authenticated customer tenant. Their `/training-media/*` routes run Worker-first and require a current member session and policy acceptance; responses are not cached. Public GitHub issue links prefill stable lesson/revision/step coordinates only, never account identity, answers, tenant evidence, or full lesson text.

Handle changes require recent authentication, current consent, CSRF, rate limits, and a live guarded identity-returning update. They preserve account IDs/provider links; a taken handle cannot merge or transfer accounts. Community activity reads repeat full ancestor visibility checks and do not add a private-branch override for moderators or owners. Expanded moderation status filters remain on the separate fresh-authorized review endpoint.

Learner accounts are pseudonymous and do not verify employment, professional status, or a Microsoft affiliation. Questions and answers are signed-in training material, not a certification exam. Completion is not certification or proof of independently acquired knowledge. The public landing page exposes only the reduced topic outline and registration/policy information.

The lesson player withholds answer feedback until the end-of-topic review; it is a teaching sequence, not an anti-cheating boundary. The authenticated catalog includes reviewed solutions. Unsubmitted answer selections can remain in per-tab browser history, validated and bound to the account, lesson, and revision. They cannot authorize member access, unlock review without a saved application attempt, or grant server completion. Module completion uses only current-revision server records.

Common secret patterns are rejected, but this is a heuristic, not a guarantee that a contribution contains no confidential information. Moderation and the participation policy remain necessary.

## Operator responsibilities

Before launch, review the terms/privacy draft and deployment gates in `HOSTING.md`. Maintain a working private reporting channel and an actual moderator. Keep the origin/RP ID stable after enrollment. Protect Cloudflare/GitHub access and backups; neither passkeys nor CSP protect against a compromised operator, build pipeline, endpoint device, or provider.

Review production CPU/usage metrics against Free-plan quotas. Configure provider visibility/alerts without logging cookie values, CSRF tokens, credential responses, passkey material, raw IPs in application logs, or contribution bodies. Authentication logs contain event names and request IDs, not credential material. Public-source failure logs may include bounded upstream error reasons.

The daily job removes expired passkey/OAuth challenges, sessions, rate buckets, and moderation audit/contact entries older than 90 days. OAuth verifiers and registration payloads are unusable after ten minutes and removed upon use or the next successful cleanup. Source-check failure or stale timestamps must remain visible; do not turn an unavailable check into an unchanged result or automatically renew lesson review dates.

A bounded independent review of the then-existing passkey, authorization, session, and member-content controls reported no high-confidence vulnerabilities on October 7, 2026; it predates the social-login extension. Contact and provider flows have targeted validation/access tests, not a claim of independent certification. This is not a guarantee of invulnerability: endpoint compromise, provider/account compromise, future changes, and configuration mistakes remain threats. Do not describe the site as absolutely “airtight.”

## Toolchain security overrides

`package.json` pins Undici 7.30.0 and Sharp 0.35.5 for the deployment/emulation tooling. Sharp includes the librsvg fix for GHSA-wq5f-xc86-pv6w. It also pins the official source-map-js 1.2.2 release to immutable upstream commit `0a1d334fd1e55a47df97fcd60a7915d46df3b08a`: the configured package feed did not yet contain that security release. This includes the indexed-section fix for GHSA-68fv-2mgg-jv7q. Keep the pins until equally verified patched versions are available; do not use an audit `--force` downgrade or replace a package with an unverified fork.

Use the private operator contact for vulnerabilities and privacy requests. Do not post credentials or exploit details involving a real organization in page discussions or public issues.
